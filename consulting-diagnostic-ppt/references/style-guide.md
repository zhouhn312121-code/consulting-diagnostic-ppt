# Style Guide

## Source Style Summary

This style is distilled from two Chinese consulting delivery PPTs:

- Marketing system current-state diagnosis and improvement recommendation report
- Sales-operation collaboration current-state diagnosis and improvement recommendation report

The shared style is a high-density, workshop-ready consulting report. It emphasizes structured diagnosis, business process decomposition, root-cause logic, management mechanisms, and implementation-oriented recommendations.

## Typical Storyline

### Broad Diagnosis

Use when diagnosing a management domain such as marketing, strategy operations, process, IT, or talent.

1. 会议议程
2. 报告目的
3. 封面
4. 项目回顾
5. 核心诊断发现
6. 建议专项破题清单
7. 下一步行动计划
8. 附录：按领域细化诊断与改进建议

### Topic Diagnosis

Use when solving a focused issue such as sales-operation collaboration, order management, planning, procurement, production, or inventory.

1. 业务体系分析
2. 现状问题分析
3. 业绩差距分析
4. 根因分析
5. 总体解决思路与专项方案
6. 下一步行动计划

## Reusable Logic Chains

### Diagnosis Chain

Use this chain on diagnosis pages:

`现状/事实 -> 问题/痛点 -> 根因 -> 影响 -> 改进建议`

Example wording:

- `D7：尚未建立战略运营管理体系，包括相应的机制与流程等，影响后期战略落地`
- `问题：提报后仍需大量汇总及分单工作`
- `根因：产品策略与计划未拉通；缺少系统工具支撑`
- `改进方向：管理侧明确规则，系统侧强化自动化能力`

### Gap Chain

Use this chain for sales, planning, order, and supply-chain topics:

`总体目标差距 -> 差距发生在哪些节令/产品/区域/人员 -> 哪些能力造成差距 -> 根因总结 -> 破局举措`

Typical dimensions:

- 节令：中秋、春节、端午
- 产品：计划品、常规品、定制品、DIY等
- 区域：大区、省区、城市、渠道
- 人员：销售经理、计划岗、采购、生产、物流
- 客户：核心客户、低产低效客户、老客户、新客户

### Process Redesign Chain

Use this chain for AS IS / TO BE pages:

`AS IS流程 -> 关键断点编号 -> 问题/根因/改进方向/效用 -> TO BE流程 -> 管理规则 + 系统能力`

When comparing the same process, prefer a stacked layout with AS IS above TO BE. Align both views by the same process stages. Mark current breakpoints with red numbers and changed steps in the future process with green. Pair the upper flow with 问题 and 根因, and the lower flow with 改进方向 and 效用与愿景.

Repeated labels:

- `AS IS`
- `TO BE`
- `问题`
- `根因`
- `改进方向`
- `效用与愿景`
- `管理侧`
- `系统侧`

## Page Types

### Agenda Page

Use a table-like layout with columns:

- 内容介绍
- 议程主责人
- 时间

Use large blue title, light-blue row bands, and strong horizontal dividers.

### Core Findings Page

Group findings by domain. Use a small percentage or count if helpful.

Domains from the reference decks:

- 战略
- 管理体系
- IT
- 人才
- 销售计划
- 需求计划
- 产销平衡机制
- 生产计划
- 采购计划
- 订单管理

Use `D1`, `D2`, etc. for broad diagnostic findings. When moving between business domains, reuse the same overview map on the left, highlight the active domain, and put its numbered findings on the right. Keep the same D number on the detail page.

### Current-State Diagnosis Page

State the issue and its business impact as one conclusion, using the D number where applicable. Put that conclusion on the same page as the evidence and mark the anomaly next to the relevant figure, screenshot, or process step. For a gap-analysis page, put the finding first, show where the gap occurs with a chart or table, and state any measurement scope or exclusions that affect interpretation. Useful evidence includes the following.

- Interview quote
- Data or chart
- Screenshot or document fragment
- Process fragment
- Responsibility/role description

Use red only for the pain point, abnormal gap, or high-priority issue.

### Improvement Recommendation Page

Recommendations must include concrete operating content:

- Organization: role定位、核心职责、能力画像
- Mechanism: 会议机制、经营分析例会、产销平衡会议
- Rule: 计划提报规则、订单优先级、安全库存规则
- Form: 数据收集清单、行动计划表、会议纪要、督办事项表
- System: 自动校验、同步ERP、物流信息同步、数据看板
- Metric: 达成率、预测偏差、准时交付率、库存周转天数

### Root-Cause Page

Use a matrix to consolidate recurring issues into a small set of supported root causes. Keep the D number and issue on the left. Organize the right side by relevant dimensions such as 策略与模式、组织与人员、流程与管理规则 and IT. Use color blocks to highlight the roots that need attention in the current project. Example categories follow.

- 计划模式及产销平衡机制需优化
- 规则不明确，缺流程指导
- IT支撑不足，应用不足
- 人员能力不足，重视度不足
- 管理体系能力待提升

### Solution Map

Start with an overview showing one goal, the implementation sequence across the main solution pillars, and their supporting special topics. Then detail the operating rules. When showing comparable channels, reuse the same department columns and place each step's lead time, prerequisites, and outputs in its corresponding stage.

Example structure:

- 目标：提升产销协同能力，保障订单履约能力，尽可能减少成本
- 总解决思路1：澄清顶层计划模式并制定相应管理规则
- 总解决思路2：通过制度化会议持续迭代管理规则
- 支撑专项：安全库存、供应商管理、采购订单、生产计划、库存数据

### Action Plan Page

Use a tracking table. Each row states the 背景 and 待办 together and identifies the 建议责任部门、主责人 and 期限. Include the 输出物 and 优先级 / 备注 where they help the handoff.

## Language Style

Use consulting-standard Chinese:

- `现状诊断`
- `核心诊断发现`
- `改进建议`
- `总体解决思路`
- `专项方案`
- `专项破题`
- `建议移交对应部门跟踪事项`
- `过程持续迭代管理规则`
- `实现精细化运营`

Prefer precise business verbs:

- 澄清
- 拉通
- 统筹
- 强化
- 赋能
- 建立
- 优化
- 牵引
- 固化
- 过程跟进

Avoid vague recommendation verbs unless followed by concrete mechanism:

- Avoid: `提升管理水平`
- Better: `建立月度经营分析例会，固化数据收集、问题决策、行动跟进三项机制`

## Typography And Colors

Observed style:

- Canvas: 16:9, 13.33 x 7.5 in
- Primary Chinese font: 微软雅黑 / Microsoft YaHei
- Common sizes: 48 pt for section or cover-level titles; 20-28 pt for major headings; 12-16 pt for body; 8-11 pt for dense tables and process maps
- Core dark blue: `#23285B`
- Consulting blue accents: `#007BBB`, `#1796FF`, `#00329F`, `#1E70CD`
- Problem red: `#C00000` or `#FF0000`
- Body black/dark gray: `#000000`, `#404040`
- Light-blue bands for agenda and table backgrounds

## Layout Habits

- Use dense but bounded page designs.
- Prefer large, full-canvas diagrams over small decorative graphics.
- Use rectangles, lines, and grouped text blocks heavily.
- Use tables for lists that need accountability or comparison.
- Use process swimlanes for cross-functional collaboration.
- Use numbered red callouts to mark pain points on flows.
- Use left-to-right or top-to-bottom logic; avoid circular decorative diagrams.
- Keep footers/page markers consistent when present.

## Common Slide Title Templates

- `X体系——本节核心诊断发现`
- `X_现状分析`
- `X_改进建议`
- `D编号：诊断结论，影响/要求`
- `改进建议：动作，目的`
- `核心根因：根因结论`
- `总体解决思路#1：动作`
- `专项N：专题名称`
- `下一步行动计划：建议移交客户对应部门跟踪事项`

## Delivery Checks

Before finalizing a deck:

- Does the deck start with why the report exists and where the project stands?
- Are findings grouped into a small number of domains?
- Does each detailed diagnosis page support a finding in the summary?
- Are recommendations specific enough for a client department to execute?
- Are process flows readable despite high density?
- Are problem numbers and recommendation numbers consistent?
- Is there a final action table for client handoff?
